## Purpose

Introduce an **Incremental Architecture Guard** system for the Zidney monorepo that validates
architectural rules **only for modules affected by a change** rather than scanning the entire
repository.

This stage upgrades the current architecture validation system so that:

• pre-commit validation is extremely fast  
• architecture rules remain strictly enforced  
• CI continues to run full validation  
• AI agents cannot accidentally violate architecture boundaries

The system integrates with:

- `ARCHITECTURE_MAP.json`
- `scripts/ai-guard.ts`
- `scripts/infra-audit.ts`
- Git dependency graph analysis

---

## Problem Statement

Current architecture validation scans the entire repository.

In a growing monorepo this causes:

• slow pre-commit checks  
• unnecessary validation work  
• reduced developer feedback speed

However, most commits only affect **one or two modules**.

Example change:

```
apps/mmc/src/views/products/ProductList.vue
```

Validating the whole repository is unnecessary when only the `apps/mmc` module is affected.

---

## Architecture Design

The Incremental Guard introduces a **Change → Module → Impact → Validation pipeline**.

```
Git Diff
   ↓
Changed Files
   ↓
Changed Modules
   ↓
Dependency Impact Resolution
   ↓
Incremental Architecture Validation
```

---

## Step 1 — Detect Changed Files

Changed files are determined using:

```
git diff --name-only
```

Example output:

```
apps/mmc/src/views/products/ProductList.vue
packages/api-client/src/client.ts
```

---

## Step 2 — Map Files to Modules

Files are mapped to modules defined in:

```
ARCHITECTURE_MAP.json
```

Example mapping:

```
apps/mmc/src/...  → apps/mmc
packages/api-client/... → packages/api-client
```

Result:

```
changed_modules = [
  "apps/mmc",
  "packages/api-client"
]
```

---

## Step 3 — Dependency Impact Resolution

Using architecture metadata and the dependency graph, determine modules affected by the change.

Example:

```
packages/domain-core changed
```

Impacted modules:

```
apps/api
apps/worker
packages/api-client
```

The validation scope becomes:

```
changed_modules + dependent_modules
```

---

## Step 4 — Incremental Validation

Architecture validation runs **only for impacted modules**.

Validation checks include:

• forbidden dependencies  
• layer violations  
• cross-layer imports  
• circular dependencies

The validation engine uses:

```
scripts/ai-guard.ts
```

---

## Step 5 — Smart Fallback

Incremental validation must automatically escalate to a **full validation** if any of the following
occur:

• `ARCHITECTURE_MAP.json` changed  
• dependency graph changed  
• new module detected  
• architecture metadata missing

Fallback command:

```
bun scripts/ai-guard.ts --full
```

## Architectural Improvement — Dependency Graph Cache

To make the Incremental Architecture Guard even faster, the dependency graph generated by
`infra-audit.ts` must be **cached and reused** instead of recomputed on every run.

### Motivation

Even incremental validation still requires knowledge of module dependencies. Recomputing the
dependency graph each time introduces unnecessary overhead.

Caching the graph allows architecture validation to remain extremely fast even as the monorepo
grows.

### Cache File

The dependency graph should be stored in:

```
docs/ai/context/ai-dependency-graph.json
```

This file is generated by:

```
bun scripts/infra-audit.ts
```

and reused by:

```
bun scripts/ai-guard.ts
```

### Cache Refresh Rules

The cache must be regenerated automatically when any of the following occur:

• a new module is added (`apps/*` or `packages/*`)  
• `ARCHITECTURE_MAP.json` changes  
• dependency imports change in source code  
• the cache file is missing

When any of these conditions occur, the guard should trigger:

```
bun scripts/infra-audit.ts --refresh-graph
```

### Performance Impact

| Operation                  | Runtime   |
| -------------------------- | --------- |
| full dependency graph scan | 300–800ms |
| cached graph reuse         | **<10ms** |

This ensures incremental validation remains within the target runtime even for large repositories.

### Governance Rule

AI agents must **never directly edit the cached dependency graph**.

The file must only be generated by:

```
infra-audit.ts
```

Manual modification would invalidate architecture guarantees.

## Architectural Improvement — Architecture Impact Report

To improve visibility of architectural effects caused by changes, the Incremental Architecture Guard
must generate an **Architecture Impact Report** during validation.

This report summarizes how a change affects the system architecture and which modules must be
validated.

### Purpose

When working in a large monorepo it can be difficult to understand the architectural impact of a
small code change.

The impact report provides:

• clear feedback for developers  
• better reasoning context for AI agents  
• faster debugging of architecture violations

### Report Output Example

Example console output produced by the guard:

```
Architecture Impact Report
--------------------------

Changed modules:
  packages/domain-core

Affected modules:
  apps/api
  apps/worker
  packages/api-client

Validation scope:
  4 modules

Validation mode:
  incremental
```

### Generation

The report should be generated automatically by:

```
bun scripts/ai-guard.ts --incremental
```

or

```
bun scripts/ai-guard.ts --full
```

### CI Integration

When running in CI, the report should also be written to:

```
docs/ai/context/architecture-impact-report.json
```

This enables:

• GitHub PR annotations  
• AI reasoning context  
• architecture debugging

### Governance Rule

The Architecture Impact Report must be generated for every architecture validation run.

AI agents must not suppress this output because it is part of the architecture governance system.

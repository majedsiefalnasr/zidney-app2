# Core Concept

Zidney's architecture is defined by **Architecture Decision Records (ADR)** stored in:

```
docs/architecture/adr/
```

Examples include:

```
ADR-0001 database-per-tenant
ADR-0002 snapshot attempt model
ADR-0003 white-label visual only
ADR-0004 single runtime engine
ADR-0005 upgrade opt-in model
ADR-0006 runtime authoritative time
ADR-0007 product version compatibility
ADR-0008 semantic versioning policy
ADR-0009 rate limiting
```

These decisions define **non-negotiable system rules**.

The Architecture Guard ensures that code changes respect these decisions.

---

# Architecture Protection Layers

Architecture protection operates in multiple layers:

```
ADR Decisions
      ↓
Architecture Guard Rules
      ↓
Dependency Graph Analysis
      ↓
AI-Guard Validation
      ↓
CI Enforcement
```

Each layer prevents architectural violations from entering the repository.

# Dependency Graph Validation

The architecture guard relies on the dependency graph generated by:

```
scripts/infra-audit.ts
```

The graph identifies relationships between:

```
apps
packages
internal modules
```

Example graph node types:

```
packages/logger
packages/domain-core
packages/api-client
apps/api
apps/mmc
apps/backoffice
apps/frontoffice
apps/worker
```

The architecture guard validates that dependencies respect the monorepo boundaries.

---

# Monorepo Layer Rules

The Zidney architecture enforces strict layering rules.

Allowed dependencies:

```
apps → packages
packages → packages
apps → local modules
```

Forbidden dependencies:

```
apps → apps
packages → apps
runtime → UI packages
UI → backend runtime
```

Example violation:

```
apps/api importing apps/mmc
```

This will be blocked by the architecture guard.

---

# ADR Enforcement Model

Each ADR represents a **contract that must be preserved**.

Example: ADR-0001 (Database Per Tenant)

Constraints:

```
no shared tenant database access
no cross-tenant queries
all tenant resolution must pass tenant-resolver
```

Architecture Guard validates that code changes do not introduce violations.

Example checks:

```
direct database connection bypass
cross-tenant joins
manual tenant ID injection
```

---

# Architecture Rule Engine

Architecture Guard rules are defined as validation checks executed by:

```
scripts/ai-guard.ts
```

Example rule categories:

```
layer violations
forbidden imports
ADR rule violations
runtime boundary violations
```

Each rule produces:

```
error
warning
report
```

Errors fail CI.

---

# AI Development Protection

AI-assisted development introduces risks where generated code may violate architecture rules.

Architecture Guard prevents this by automatically validating:

```
imports
module dependencies
ADR compliance
runtime boundaries
```

This ensures that AI-generated code cannot break system architecture.

---

# CI Integration

Architecture validation runs in CI before tests.

Recommended pipeline order:

```
Biome
AI-Guard
Architecture Guard
Infra Audit
Vitest
Playwright
```

Early failure prevents architecture violations from propagating.

---

# Architecture Drift Detection

Architecture drift occurs when the system gradually deviates from its original design.

Architecture Guard prevents drift by:

```
tracking dependency graph changes
comparing architecture snapshots
validating ADR contracts
blocking forbidden imports
```

Drift detection reports are generated automatically.

---

# Developer Workflow

Developers do not interact directly with Architecture Guard.

Instead they run:

```
bun run ai-guard
```

or rely on the CI pipeline.

If a violation occurs, the system reports:

```
violated rule
file location
recommended fix
```

# Governance Responsibilities

Architecture ownership belongs to the platform architecture layer.

Changes affecting architecture must:

```
update ADR documents
update AI-Guard rules
pass architecture validation
```

This prevents undocumented architecture changes.

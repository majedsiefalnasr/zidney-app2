## Manual Test Scenarios

### Scenario 1 — Create subject (happy path)

**Purpose:** Verify create flow and DB write

1. POST `/api/v1/backoffice/workspace/subjects` with valid body (name, code, divisionId, semesterId)
2. Expect 201 and returned `id`
3. Verify row in tenant DB `subjects` table with given `code` and `name`

Expected: Subject created, unique constraints enforced.

### Scenario 2 — Transition DRAFT→ACTIVE (CAS)

**Purpose:** Verify transition uses CAS and returns 409 on conflict

1. POST `/.../subjects/:id/transition` with `{ to: 'ACTIVE', expectedUpdatedAt: '<timestamp>' }`
2. If another update occurred, API returns 409 `SUBJECT_TRANSITION_CONFLICT`
3. Retry after fetching fresh subject and expectedUpdatedAt

Expected: CAS prevents lost updates; client can retry.

### Scenario 3 — Delete subject with dependent content

**Purpose:** Ensure deletion is blocked when dependencies exist

1. Attempt DELETE on a subject that has downstream dependent content (not present at STAGE_28)
2. Expect 422 `SUBJECT_HAS_DEPENDENT_CONTENT` if dependencies exist

Expected: Deletion guarded; currently registry empty so deletion succeeds for clean subjects.

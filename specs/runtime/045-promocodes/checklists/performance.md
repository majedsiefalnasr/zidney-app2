## Index Strategy Requirements

- [ ] CHK001 - Is the case-insensitive unique index (`idx_promocodes_code_lower` on `LOWER(code)`) specified as the primary lookup path for all code validation queries — and are requirements for query routing to use this index documented? [Completeness, Spec §DB Schema]
- [ ] CHK002 - Is the partial index (`idx_promocodes_active` with `WHERE is_active = TRUE`) specified as the targeted index for list/search queries that filter by active status and validity window — minimizing scan scope? [Clarity, Spec §DB Schema]
- [ ] CHK003 - Are index requirements defined for the `valid_from`/`valid_until` range query pattern in the listing endpoint's `status` filter? A composite index on `(is_active, valid_until)` may be needed. [Gap, Spec §FR-02]
- [ ] CHK004 - Is the `idx_promocode_usages_promocode` index (on `promocode_id`) specified as sufficient for global usage count queries, or are additional composite indexes required for the analytics aggregate queries? [Ambiguity, Spec §DB Schema]
- [ ] CHK005 - Is the `idx_promocode_usages_student_promocode` index on `(student_id, promocode_id)` specified as supporting per-user limit counting — and is its covering ability confirmed for both `COUNT(*)` and `FOR UPDATE` lock patterns? [Clarity, Spec §DB Schema, FR-10]
- [ ] CHK006 - Are index requirements defined for the analytics endpoint's aggregate queries (`revenue_impact` sum, `top_codes` ranking)? Repeated full-table aggregation over `promocode_usages` without strategy could become expensive at volume. [Gap, Spec §FR-14]
- [ ] CHK007 - Is the unique index on `(promocode_id, subscription_id)` in `promocode_usages` specified both as a correctness constraint and as a performance optimization for deduplication lookups? [Completeness, Spec §DB Schema]

## N+1 Query Prevention Requirements

- [ ] CHK008 - Is the usage count sub-query on the listing endpoint (`FR-02`: "Response includes current usage count per code") specified as a single SQL aggregate (e.g., `LEFT JOIN` sub-select or `COUNT()` window function) — not as a per-row follow-up query? [Clarity, Spec §FR-02]
- [ ] CHK009 - Are requirements defined for the analytics endpoint to retrieve all aggregate metrics in a bounded number of queries (e.g., 1–2 queries) rather than iterating over code rows? [Gap, Spec §FR-14]
- [ ] CHK010 - Is the `getPromocode` by ID endpoint with analytics (`total_usages`, `revenue_impact`, `usages_by_division`, `usages_by_group`) specified to be fetched within a defined number of queries? Without this, adding each `usages_by_*` breakdown is a hidden N+1 risk. [Gap, Spec §FR-03, FR-14]
- [ ] CHK011 - Is the student targeting check (loading `division_id` and `group_id` from the `students` table) specified to run at most once per validation call — not once inside the validator and once inside the service? [Ambiguity, Spec §FR-12]
- [ ] CHK012 - Are requirements defined for how `top_codes` (top 10 by redemptions) is retrieved — single ranked query vs. in-memory sort over all codes? [Gap, Spec §FR-14]

## Transaction Scope & Lock Contention Requirements

- [ ] CHK013 - Is the SERIALIZABLE transaction scope specified as tightly bounded (opened immediately before the lock acquire, closed immediately after the `promocode_usages` insert) — not spanning the full HTTP request lifecycle? [Clarity, Spec §FR-09, applyPromocode]
- [ ] CHK014 - Are requirements defined for whether the `FOR UPDATE` lock on usage counts acquires a row-level or table-level lock? A table-level lock would serialize all concurrent applications globally. [Ambiguity, Spec §FR-10, FR-11]
- [ ] CHK015 - Is the lock duration during the subscription creation transaction acceptable under the expected concurrency load? Are requirements defined for maximum acceptable lock-wait timeout? [Gap, Spec §FR-09]
- [ ] CHK016 - Are requirements defined for transaction retry behavior when a serialization failure occurs (Postgres 40001), including a maximum retry count to prevent indefinite lock thrashing? [Gap, Spec §FR-09]
- [ ] CHK017 - Is the `pre-validation` call (`PromocodeService.validatePromocode()` before opening the transaction) specified to run outside the transaction — ensuring the SERIALIZABLE transaction is kept as short as possible? [Clarity, Spec §FR-13, applyPromocode]

## Concurrent Usage & High-Throughput Requirements

- [ ] CHK018 - Are performance requirements (e.g., latency SLOs) defined for the validate endpoint under concurrent load — especially since it runs all 7 checks synchronously? [Gap]
- [ ] CHK019 - Are requirements defined for behavior when many concurrent requests apply the last available slot for a usage-limited code? Is the expected failure mode specified (reject with `USAGE_LIMIT_REACHED`, no silent data loss)? [Completeness, Spec §FR-11]
- [ ] CHK020 - Is the high-concurrency stacking scenario (multiple simultaneous `applyPromocode` calls for the same subscription) addressed in requirements — specifying which caller wins and which fails? [Gap, Spec §FR-08]
- [ ] CHK021 - Is expected throughput or concurrent request volume estimated for the subscription creation endpoint with promo attachment? Without this, the lock contention risk cannot be assessed. [Gap, Spec §FR-09]

## Query Efficiency Requirements

- [ ] CHK022 - Is the validity-status filter in listing (`ACTIVE_NOW`, `EXPIRED`, `NOT_YET_VALID`, `INACTIVE`) specified to be computed as a SQL predicate (not post-query filtering in application code)? [Clarity, Spec §FR-02]
- [ ] CHK023 - Is a maximum page size defined for the listing endpoint to prevent unbounded full-table scans? The spec specifies `default limit = 20` but does not state a maximum. [Ambiguity, Spec §FR-02]
- [ ] CHK024 - Are requirements defined for how `usages_remaining` (computed field in single-code analytics) is calculated — via `usage_limit - COUNT(*)` in one query or via two separate queries? [Gap, Spec §FR-03]
- [ ] CHK025 - Are requirements defined for analytics response freshness? If counts are computed live on every request, are there caching or materialization requirements to prevent repeated expensive aggregates? [Gap, Spec §FR-14]
- [ ] CHK026 - Is the `revenue_impact` aggregate (`SUM(discount_amount)`) over all historical `promocode_usages` rows specified with a performance note — as this table grows unbounded with no deletion policy? [Gap, Spec §FR-14]

## Pagination & Data Volume Requirements

- [ ] CHK027 - Is the `top_codes` result set in analytics specified as a server-side LIMIT 10 query — not a full result set sorted in application memory? [Completeness, Spec §FR-14]
- [ ] CHK028 - Are query performance expectations defined for the `usages_by_division` and `usages_by_group` breakdowns in single-code analytics — particularly as usage volume grows? [Gap, Spec §FR-14]
- [ ] CHK029 - Are pagination requirements defined for the `promocode_usages` history if/when it is exposed — or is it explicitly out of scope for this stage? [Gap]
- [ ] CHK030 - Is the `applies_to_plan_ids` JSONB array specified to have a maximum cardinality limit to prevent performance degradation in the plan eligibility check (Check 6) under a large plan set? [Gap, Spec §FR-06 / Validation Engine]

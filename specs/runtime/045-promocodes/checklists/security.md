## Tenant Isolation Requirements

- [ ] CHK001 - Are requirements explicit that promotional codes are scoped exclusively to the tenant database and can never be shared, read, or inferred from another tenant? [Completeness, Spec §Architecture Governance]
- [ ] CHK002 - Is it specified that the tenant DB connection is resolved from the slug before any promocode operation, making cross-tenant access structurally impossible (not just conditionally filtered)? [Clarity, Spec §Trust Chain]
- [ ] CHK003 - Are integration test requirements defined that assert a code from Tenant A cannot be applied, validated, or fetched from Tenant B's request context? [Coverage, Spec §Integration Tests]
- [ ] CHK004 - Is the prohibition on shared promocode tables (row-based multi-tenancy) stated as a hard non-goal rather than an implementation note? [Consistency, Spec §Non-Goals]
- [ ] CHK005 - Are requirements for the analytics endpoint scoped to prevent cross-tenant aggregate leakage? [Gap, Spec §FR-14]

## Authentication & Authorization Requirements

- [ ] CHK006 - Are role requirements (admin only) explicitly stated for every promocode route, not merely implied by middleware ordering? [Completeness, Spec §API Endpoints]
- [ ] CHK007 - Is the order of middleware gates (tenant resolver → license → auth) specified as a hard constraint rather than a convention? [Clarity, Spec §Trust Chain]
- [ ] CHK008 - Are requirements defined for what happens if authentication middleware is absent or misconfigured on a new promocode route? [Gap, Edge Case]
- [ ] CHK009 - Is the student-facing vs. admin-facing access boundary explicitly defined? The spec defers public code submission to a future stage — is this scope exclusion clearly documented as a security boundary? [Clarity, Spec §Non-Goals]
- [ ] CHK010 - Are requirements defined for re-authentication or session validation during a long-lived subscription creation flow that includes promo validation? [Gap]

## Input Validation Requirements

- [ ] CHK011 - Are all input fields for `createPromocodeBodySchema` specified with explicit type, length, format, and rejection behavior rather than relying on DB constraint enforcement alone? [Clarity, Spec §Validation Schemas]
- [ ] CHK012 - Is the maximum length constraint for the `code` field (100 characters) specified at the Zod schema layer, not only at the DB column layer? [Completeness, Spec §DB Schema / Validation Schemas]
- [ ] CHK013 - Is the character set or pattern restriction for the `code` field specified? (e.g., are Unicode homograph attacks or whitespace injection addressed?) [Ambiguity, Spec §FR-01]
- [ ] CHK014 - Are conditional validation rules (type-specific field presence) specified as Zod discriminated union or `.superRefine()` — not left to runtime guards that could be bypassed? [Clarity, Spec §Validation Schemas]
- [ ] CHK015 - Are `target_division_ids` and `target_group_ids` specified to be validated as arrays of UUIDs rather than arbitrary strings? [Completeness, Spec §FR-12]
- [ ] CHK016 - Is `applies_to_plan_ids` specified to be validated as a non-negative-length array of UUIDs with a defined maximum length? [Gap]
- [ ] CHK017 - Are date fields (`valid_from`, `valid_until`) specified to be parsed and normalized server-side to UTC before storage, with client-supplied timezone offset explicitly rejected or ignored? [Clarity, Spec §FR-01]
- [ ] CHK018 - Is the numeric precision for `value` (numeric(10,2)) enforced at the schema layer to prevent floating-point injection that could produce unexpected discount amounts? [Gap]

## SQL Injection Prevention Requirements

- [ ] CHK019 - Is it specified that all database access uses Drizzle ORM parameterized queries exclusively — with a policy statement that raw SQL strings are forbidden in domain code? [Completeness, Spec §Domain Modules]
- [ ] CHK020 - Is the case-insensitive code lookup (`LOWER(code)`) specified to go through a parameterized query interface rather than string interpolation? [Clarity, Spec §DB Schema]
- [ ] CHK021 - Are JSONB array fields (`applies_to_plan_ids`, `target_division_ids`, `target_group_ids`) specified to be stored via parameterized binding and queried only with array operators — not string-interpolated into SQL IN clauses? [Completeness, Spec §DB Schema]
- [ ] CHK022 - Is there a requirement that the `status` filter in `listPromocodesQuerySchema` is validated against an enum before use in a query predicate? [Gap, Spec §FR-02]

## Race Condition & Concurrency Safety Requirements

- [ ] CHK023 - Are the `FOR UPDATE` lock requirements for usage count checks specified at the row or aggregate level, and is the target lock scope (promocode row, aggregate count, or both) unambiguous? [Clarity, Spec §FR-10, FR-11]
- [ ] CHK024 - Is the SERIALIZABLE isolation level specified as the requirement for the combined subscription + usage insert transaction — with rationale that a lower level (e.g., READ COMMITTED) is insufficient? [Clarity, Spec §FR-09]
- [ ] CHK025 - Is the double-validation requirement (re-validate inside the transaction after acquiring the lock) specified as mandatory, not as an optimization? [Completeness, Spec §PromocodeService / applyPromocode]
- [ ] CHK026 - Are requirements defined for handling a transaction serialization failure (PostgreSQL error code 40001) — retry policy, user-facing error, or both? [Gap, Edge Case]
- [ ] CHK027 - Is the `(promocode_id, subscription_id)` unique index on `promocode_usages` specified as a concurrency guard (not just a data integrity rule) that prevents double-apply even under concurrent requests? [Clarity, Spec §DB Schema]

## Rate Limiting Requirements

- [ ] CHK028 - Are rate limiting requirements defined for the `/validate` endpoint? Without a limit, this endpoint is usable as a brute-force code enumeration vector. [Gap, Spec §API Endpoints - Validate]
- [ ] CHK029 - Are rate limiting requirements defined for `POST /backoffice/promocodes/validate` to prevent automated probing of valid code + student + plan combinations? [Gap, Security Risk]
- [ ] CHK030 - Are rate limiting requirements defined for subscription creation (`POST /backoffice/subscriptions`) to prevent promo-code exhaustion attacks via rapid concurrent requests? [Gap, Spec §FR-11]
- [ ] CHK031 - Is the rate limiting policy (per-IP, per-tenant, per-admin, or combined) specified — or explicitly declared out of scope with a ticket reference? [Ambiguity]

## Discount Calculation & Client Trust Requirements

- [ ] CHK032 - Is the server-only discount calculation rule stated explicitly as a security requirement (not just an implementation note), with a prohibition on accepting any client-supplied `discount_amount`? [Completeness, Spec §Architecture Governance]
- [ ] CHK033 - Is the gateway callback re-validation requirement specified as a security control — discarding the gateway-reported amount and recalculating server-side? [Clarity, Spec §FR-13]
- [ ] CHK034 - Is the behavior on gateway callback re-validation failure specified as "reject + log + alert" rather than "accept with best-effort"? [Clarity, Spec §FR-13]
- [ ] CHK035 - Are requirements defined for logging a security event when the gateway-reported discount differs from the server-recalculated amount? [Gap]

## Data Exposure & Information Leakage Requirements

- [ ] CHK036 - Is it specified that the `/validate` endpoint returns rejection reason codes (e.g., `PROMOCODE_EXPIRED`) without leaking whether a code exists for a guessed value? (i.e., does `PROMOCODE_NOT_FOUND` leak the non-existence of all codes?) [Ambiguity, Spec §Error Codes]
- [ ] CHK037 - Are analytics response fields (`revenue_impact`, `top_codes`) restricted to admin role — with no path by which a non-admin authenticated user could access revenue aggregates? [Completeness, Spec §FR-14]
- [ ] CHK038 - Is it specified that the `/backoffice/promocodes/:id` response excludes raw `student_id` lists and only returns aggregated usage counts? [Completeness, Spec §FR-03]
- [ ] CHK039 - Is the MMC exclusion from student-level promocode data stated as a security boundary, not just a product decision? [Clarity, Spec §FR-14]

## Immutability & History Preservation Requirements

- [ ] CHK040 - Is code immutability (`code`, `type`, `value` after creation) defined as a security invariant to prevent retroactive code downgrade or coupon fraud — not just a UX constraint? [Clarity, Spec §FR-05]
- [ ] CHK041 - Is the prohibition on deleting `promocode_usages` rows specified as a security/audit requirement (tamper-evident log) rather than only a functional requirement? [Clarity, Spec §Architecture Governance]
- [ ] CHK042 - Are requirements defined for what happens if a DELETE on `promocode_usages` is attempted (e.g., should the API return 405 Method Not Allowed or 403 Forbidden)? [Gap, Edge Case]

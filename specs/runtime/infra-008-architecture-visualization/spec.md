## Feature Overview

### What Is Being Built

STAGE_INFRA_08_ARCHITECTURE_VISUALIZATION introduces a **dedicated architecture visualization pipeline** for the Zidney monorepo.

The foundation already exists. `scripts/infra-audit.ts` produces raw Mermaid files in `docs/architecture/graphs/` as a by-product of its scan. These files are machine-generated from unfiltered import traces and serve the audit system's internal needs. They are noisy (containing deep submodule paths, duplicate edges, and external package references) and are not optimized for human or AI readability.

This stage closes the gap by introducing `scripts/architecture/visualize.ts`: a standalone script that **reads the audit output** and **produces clean, curated, human-readable Mermaid diagrams** in `docs/architecture/visualization/`. The visualization pipeline is read-only and does not modify any architecture data or governance files.

Visualization ensures that architecture is not only enforced (via `ai-guard.ts`) and measured (via `infra-audit.ts`) but also **observable and explainable**.

## Background & Motivation

### The Problem

The Zidney monorepo has a mature architecture enforcement system after stages INFRA-01 through INFRA-07. However, architecture documentation remains a blind spot:

1. **Raw graphs are unreadable.** The Mermaid files in `docs/architecture/graphs/` are generated by `infra-audit.ts` from unfiltered import traces. They include thousands of edges, deep submodule paths (`./apps/mmc/src/core/auth/token-manager`), external library references, and duplicate entries. These files serve machine consumers but fail human and AI readers.

2. **No curated module-level view exists.** There is no single file that shows only the 13 top-level modules (`apps/*` and `packages/*`) and their dependencies with layer annotations. This view is the most important for understanding architectural health.

3. **No layer diagram with cross-layer edges.** The existing `architecture-overview.mmd` shows layers and their member modules but omits the inter-module dependency arrows that make architectural analysis meaningful.

4. **No system-level trust chain diagram.** The Zidney trust chain (Isolation → License → Authentication → Attempt → Runtime → Frontoffice) is documented in text but has no visual representation in the repository.

5. **AI agents lack a dedicated visual context directory.** AI tools that assist with development need a stable location for human-readable architecture diagrams. The raw graphs in `docs/architecture/graphs/` are too noisy to be useful; the AI context files in `docs/ai/context/` are JSON-structured for machine parsing. A human-readable intermediary is missing.

### The Solution

A dedicated `scripts/architecture/visualize.ts` script that:

1. Reads structured data from existing audit outputs (`docs/architecture/graphs/dependency-graph.json`, `docs/architecture/intelligence/ARCHITECTURE_MAP.json`)
2. Filters and deduplicates edges to produce module-level diagrams
3. Applies layer classifications from `ARCHITECTURE_MAP.json` to generate layered views
4. Writes clean Mermaid `.mmd` files and a Markdown index to `docs/architecture/visualization/`
5. Runs in under five seconds with no external dependencies beyond Bun and Node built-ins

## Data Sources

The visualization script reads exclusively from files that already exist on disk, produced by prior pipeline steps.

### Primary Input: Dependency Graph

**File**: `docs/architecture/graphs/dependency-graph.json`  
**Produced by**: `scripts/infra-audit.ts` (via `bun run arch:audit`)  
**Format**: JSON with `nodes: string[]` and `edges: { from: string; to: string }[]`  
**Used for**: Module nodes and dependency edges

This file contains both top-level module nodes (`apps/api`, `packages/logger`) and deep submodule paths (`./apps/mmc/src/core/auth`). The visualize script **filters to top-level modules only** (paths matching `apps/<name>` or `packages/<name>` with exactly two path segments).

### Secondary Input: Architecture Map

**File**: `docs/architecture/intelligence/ARCHITECTURE_MAP.json`  
**Produced by**: `scripts/architecture/generate-architecture-map.ts` and updated by `scripts/infra-audit.ts --fix-map`  
**Format**: JSON with `layers: string[]` and `modules: Record<string, { layer, description, criticality, allowed_dependencies, forbidden_dependencies }>`  
**Used for**: Layer classification of each module (domain / infrastructure / runtime / ui)

## Developer Scenarios & Testing

### Scenario 1 — Developer Generates Architecture Diagrams (Priority: P1)

A developer wants to visualize the current state of the Zidney architecture before reviewing a PR that introduces a new package.

**Why this priority**: This is the primary use case. It must work correctly and produce readable output.

**Independent Test**: Run `bun run arch:visualize`, verify exit code 0, verify three `.mmd` files and one `README.md` exist in `docs/architecture/visualization/`, verify all diagram files contain valid Mermaid syntax.

**Acceptance Scenarios**:

1. **Given** `docs/architecture/graphs/dependency-graph.json` and `docs/architecture/intelligence/ARCHITECTURE_MAP.json` exist, **When** `bun run arch:visualize` is run, **Then** the command exits with code 0, prints `[VISUALIZE] Done — 3 diagrams written to docs/architecture/visualization/`, and four files exist in `docs/architecture/visualization/`.

2. **Given** the generated `module-dependency-graph.mmd`, **When** the file is inspected, **Then** it contains only top-level module nodes (no deep submodule paths like `./apps/mmc/src/core/auth`), contains no duplicate edges between the same pair of modules, and each node is annotated with its layer (ui / runtime / domain / infrastructure) using Mermaid subgraph syntax or node labels.

3. **Given** the generated `layer-architecture-diagram.mmd`, **When** the file is inspected, **Then** it contains four `subgraph` blocks (UI, Runtime, Domain, Infrastructure), each module appears in exactly one subgraph, and edges between modules appear below the subgraph declarations with arrows pointing from dependent to dependency (e.g., `apps_api --> packages_domain_core`).

4. **Given** the generated `system-overview-diagram.mmd`, **When** the file is inspected, **Then** it contains the five named Zidney services (MMC, Backoffice, Frontoffice, API, Worker), shows the trust chain flow (UI → API → Worker), and includes the foundational packages (domain-core, logger, types, config, redis-utils).

5. **Given** the output `README.md`, **When** the file is read, **Then** it contains a header, generation date, link or reference to each of the three diagram files, and renders instructions for viewing Mermaid in GitHub or compatible tooling.

4. **Given** successful previous run produced files in `docs/architecture/visualization/`, **When** `bun run arch:visualize` is run again with the same input, **Then** the output files are identical to the previous run (deterministic output).

### Scenario 3 — AI Agent Reads Architecture Diagrams (Priority: P2)

An AI agent (GitHub Copilot, Claude, Cursor) is helping a developer add a new package. The agent loads architecture context from `docs/architecture/visualization/README.md` to understand boundaries before generating code.

**Why this priority**: AI assisted development quality improves when the agent has explicit, readable architecture context. This scenario validates that the output format is useful for AI consumption.

**Independent Test**: Read the generated README.md and diagram files and verify they contain enough context for an AI agent to understand: (1) which layer a new module should belong to, (2) what existing modules it may depend on, and (3) the trust chain flow.

**Acceptance Scenarios**:

1. **Given** `docs/architecture/visualization/README.md` exists, **When** an AI agent reads it, **Then** the file identifies all 13 registered modules, their layer assignments, and provides a brief explanation of the dependency direction rules.

2. **Given** the `layer-architecture-diagram.mmd`, **When** an AI agent reads it, **Then** the file allows the agent to identify — without loading ARCHITECTURE_MAP.json — which layer `packages/domain-core` belongs to and which apps depend on it.

3. **Given** a developer asks an AI agent "which modules can `packages/validation` depend on?", **When** the agent reads the layer diagram, **Then** the agent can correctly answer using only the visualization output.

---

### Edge Cases

- What happens when `dependency-graph.json` has zero edges? → The script produces valid (but empty) Mermaid files with only node declarations. No crash.
- What happens when a module exists in `dependency-graph.json` but is absent from `ARCHITECTURE_MAP.json`? → The module is rendered in an `Unknown` subgraph with a warning printed: `[VISUALIZE] WARNING: No layer found for module <name> — classified as Unknown`.
- What happens when `docs/architecture/visualization/` does not exist? → The script creates it with `mkdirSync({ recursive: true })` before writing any files.
- What happens when a diagram file already exists from a previous run? → It is silently overwritten (same input always produces same output).
- What happens when `dependency-graph.json` contains deep submodule paths alongside top-level module paths? → The script filters to retain only paths with exactly two slash-separated segments starting with `apps/` or `packages/`. All sub-paths are discarded.

## Functional Requirements

### FR-001 — Visualization Script Created

A new script `scripts/architecture/visualize.ts` must be created in the existing `scripts/architecture/` directory alongside `add-module.ts` and `generate-architecture-map.ts`.

The script must:

- Be executable with `bun scripts/architecture/visualize.ts`
- Export its primary logic as named functions for unit testing
- Use only Node.js built-in modules (`node:fs`, `node:path`) and Bun runtime APIs — no new npm packages
- Include a `// CLI utility — exempt from service-layer logging standards.` note consistent with other scripts in the directory

### FR-002 — Read Dependency Graph

The script must read `docs/architecture/graphs/dependency-graph.json` relative to the repository root (resolved via `process.cwd()`).

If the file does not exist, the script must exit with code 1 and print a clear error with the command to run first (`bun run arch:audit`).

If the file exists but cannot be parsed as valid JSON, the script must exit with code 1 and print the parse error.

### FR-003 — Read Architecture Map

The script must attempt to read `docs/architecture/intelligence/ARCHITECTURE_MAP.json` relative to the repository root.

If the file does not exist, the script must continue using heuristic layer classification (see FR-007) and print a warning.

If the file exists but cannot be parsed as valid JSON, the script must continue with heuristic classification and print a warning.

### FR-004 — Generate Module Dependency Graph

The script must write `docs/architecture/visualization/module-dependency-graph.mmd` containing a Mermaid `graph TD` diagram that shows:

- **Nodes**: All top-level modules (paths matching `apps/<name>` or `packages/<name>` — exactly two path segments) from the dependency graph
- **Edges**: Deduplicated dependency edges between top-level modules (one edge per unique `from → to` pair, regardless of how many times it appears in the raw graph)
- **Layer subgraphs**: Modules grouped by layer using Mermaid `subgraph` blocks (UI, Runtime, Domain, Infrastructure)
- **Safe node IDs**: All node IDs must replace `/` and `-` with `_` to produce valid Mermaid identifiers (e.g., `apps/api` → `apps_api`)
- **Display labels**: Each node must display its full path as a label (e.g., `apps_api["apps/api"]`)

Deep submodule paths (containing more than two path segments, or starting with `./`) must be excluded from this diagram entirely.

### FR-005 — Generate Layer Architecture Diagram

The script must write `docs/architecture/visualization/layer-architecture-diagram.mmd` containing a Mermaid `graph TD` diagram that shows:

- **Four subgraph blocks**: `UI`, `Runtime`, `Domain`, `Infrastructure` — each containing the modules assigned to that layer in ARCHITECTURE_MAP.json (or heuristic fallback)
- **Cross-subgraph edges**: All deduplicated dependency edges between top-level modules, shown outside the subgraph declarations
- **Direction**: Arrows point from the dependent module to the dependency (consumer → provider), consistent with the `UI → Runtime → Domain → Infrastructure` layering model

This diagram is intended to make layer violations visually obvious: any edge pointing against the direction model (e.g., Domain → UI) indicates an architectural problem.

### FR-006 — Generate System Overview Diagram

The script must write `docs/architecture/visualization/system-overview-diagram.mmd` containing a Mermaid `graph TD` diagram that shows:

- **Five application nodes**: `MMC`, `Backoffice`, `Frontoffice`, `API`, `Worker` — with display labels and shape annotations (UI apps as rectangles, backend services as rounded boxes)
- **Trust chain flow**: Arrows showing the Zidney trust chain:
  - UI layer → API (MMC → API, Backoffice → API, Frontoffice → API)
  - API → Worker (asynchronous job delegation)
- **Foundational package group**: A subgraph `Foundation` containing `packages/domain-core`, `packages/logger`, `packages/types`, `packages/config`, `packages/redis-utils`
- **Foundation connections**: Arrows from API and Worker to the Foundation subgraph

This diagram is static and annotated. It is not derived from the dependency graph dynamically — it reflects the Zidney platform topology as defined by the Trust Chain model in AGENTS.md and PROJECT_CONTEXT_PRIMER.md.

### FR-007 — Heuristic Layer Classification

When `ARCHITECTURE_MAP.json` is unavailable or unparseable, the script must classify modules using the following heuristic:

| Module Path Pattern    | Heuristic Layer |
| ---------------------- | --------------- |
| `apps/mmc`             | ui              |
| `apps/backoffice`      | ui              |
| `apps/frontoffice`     | ui              |
| `apps/api`             | runtime         |
| `apps/worker`          | runtime         |
| `packages/ui-system`   | ui              |
| `packages/api-client`  | infrastructure  |
| `packages/domain-core` | domain          |
| `packages/validation`  | domain          |
| `packages/types`       | domain          |
| `packages/logger`      | infrastructure  |
| `packages/config`      | infrastructure  |
| `packages/redis-utils` | infrastructure  |
| Any unrecognized path  | unknown         |

### FR-008 — Generate Visualization README

The script must write `docs/architecture/visualization/README.md` containing:

- A brief description of the visualization pipeline and its data sources
- The generation timestamp (ISO 8601)
- The git SHA used during generation (from `git rev-parse HEAD`)
- A reference section listing all three diagram files with one-line descriptions
- Instructions for viewing Mermaid diagrams (GitHub renders `.mmd` inline; VS Code requires the Mermaid Preview extension)
- A note that this directory is **auto-generated** and changes will be overwritten by the next `bun run arch:visualize` run (humans should not edit files here)

### FR-009 — Package.json Script Entry

The `package.json` at the repository root must gain a new script entry:

```json
"arch:visualize": "bun scripts/architecture/visualize.ts"
```

This script must be placed adjacent to the existing `arch:` family of scripts (`arch:audit`, `arch:guard`, `arch:add-module`, `arch:generate`, `arch:context`, `arch:refresh`, `arch:fix`).

### FR-010 — No New External Dependencies

The script must not introduce any new entries in the top-level `package.json` `devDependencies` or `dependencies`. All required functionality must be implemented using:

- Node.js built-in modules: `node:fs`, `node:path`, `node:child_process` (for git SHA)
- Bun runtime intrinsics available without installation

If a future enhancement requires a charting library (e.g., `@mermaid-js/mermaid-cli` for SVG rendering), it must be proposed in a separate ADR and implemented in a future stage.

### FR-011 — Deterministic Output

Given identical input files (`dependency-graph.json` and `ARCHITECTURE_MAP.json`), the script must produce byte-identical output on every run. This means:

- Node ordering must be stable (sort alphabetically by module path)
- Edge ordering must be stable (sort alphabetically by `from`, then `to`)
- Timestamps in `README.md` are the only non-deterministic element and are acceptable

### FR-012 — Output Directory Creation

If `docs/architecture/visualization/` does not exist when the script runs, it must be created automatically using `mkdirSync({ recursive: true })` before any write operations. The script must not fail if the directory already exists.

## Non-Functional Requirements

### NFR-001 — Performance

The script must complete in under 5 seconds on any developer machine with the current monorepo size (13 modules, ~800 dependency edges). No blocking I/O loops or redundant file reads.

### NFR-002 — Read-Only Guarantee

The visualization script is strictly read-only with respect to architecture data. It must not:

- Modify `docs/architecture/graphs/dependency-graph.json`
- Modify `docs/architecture/intelligence/ARCHITECTURE_MAP.json`
- Modify `docs/architecture/intelligence/ARCHITECTURE_CONTRACT.json`
- Modify `docs/ai/context/` files
- Modify any migration or schema file

The only files it may write are within `docs/architecture/visualization/`.

### NFR-003 — CI Compatibility

The script must follow these CI conventions:

- Exit code `0` on successful generation
- Exit code `1` on any fatal error (missing required input, parse failure)
- All user-facing messages prefixed with `[VISUALIZE]`
- Structured log lines to `stdout` (no `console.error` / `console.warn` for warnings; use `console.log` with severity prefix)
- Compatible with Bun v1.x runtime (same version used by all other `scripts/` files)

### NFR-004 — Layer Boundary Compliance

The `scripts/architecture/visualize.ts` file must itself comply with Zidney architecture rules:

- It lives in the `scripts/` infrastructure layer
- It reads from `docs/architecture/` and `docs/ai/context/` (allowed read targets)
- It has no imports from `apps/*` or `packages/*`
- It uses only Node.js built-ins (no cross-layer imports)

## Success Criteria

1. **Developer generates diagrams in one command**: Running `bun run arch:visualize` on a machine with a current `arch:audit` output produces three Mermaid diagram files and a README in `docs/architecture/visualization/` within 5 seconds.

2. **Module dependency graph is readable**: The generated `module-dependency-graph.mmd` contains only the 13 registered top-level modules (no deep submodule paths), deduplicated edges, and visible layer groupings — making the current dependency structure understandable at a glance.

3. **Layer architecture diagram exposes violations**: Any dependency that crosses layer boundaries in the wrong direction (e.g., a domain package importing a UI package) is immediately visible as an arrow pointing against the layer flow in the generated diagram.

## AI Integration Notes

| File                                        | Format   | Consumer          |

AI tools that support Markdown and Mermaid (GitHub Copilot, Claude, Cursor) can reason about architecture using the visualization directory without parsing raw JSON.

## Explicit Non-Goals

- **SVG/PNG generation**: Raster image export requires a headless browser or CLI renderer — out of scope for this stage.
- **Interactive diagrams**: The existing `docs/architecture/graphs/architecture-graph.html` already provides interactivity via vis.js — no new interactive format is needed.
- **Real-time update on file save**: Watch mode for the visualize script is not needed; developers run it explicitly after `arch:audit`.
- **Violation highlighting in diagrams**: The diagrams visualize the current state without distinguishing compliant vs. violating edges — that is the job of `ai-guard.ts` and `infra-audit.ts`.
- **Mermaid rendering validation**: The script generates valid Mermaid source but does not invoke a Mermaid parser to validate the output — developers use GitHub or VS Code for rendering.
- **Modifying `.husky/pre-commit`**: Visualization is not added to the pre-commit hook; it is an on-demand developer tool.
